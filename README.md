# Эффективность 360
### Сервис подготовки и сопровождения внутренних заявок на служебные командировки

**«Эффективность 360»** — сервис, который помогает сотрудникам правильно оформлять служебные командировки, проверяет полноту заявок по нормативным требованиям и сопровождает их рассмотрение работодателем.

Система преобразует описание потребности в структурированную заявку, выявляет недостающие сведения, показывает нормативные основания требований и помогает ответственным сотрудникам контролировать процесс рассмотрения.

## 1. Проблема и решение

Подготовка внутренних заявок часто требует знания нормативных требований, заполнения множества полей и взаимодействия с несколькими ответственными сотрудниками.

Это приводит к неполным заявкам, повторным уточнениям, задержкам и дополнительной нагрузке на административные подразделения.

**«Эффективность 360» решает эту задачу за счёт единого цифрового процесса:**

- структурирует обращение сотрудника;
- проверяет наличие обязательных сведений;
- показывает основания требований и причины блокировки;
- сопровождает отправку и рассмотрение заявки;
- сохраняет историю решений и обеспечивает прозрачность процесса.

## 2. Как работает сервис

1. **Обращение.** Сотрудник описывает потребность в свободной форме.
2. **Подготовка.** Сервис переводит обращение в процесс заполнения структурированной заявки.
3. **Проверка.** Система проверяет полноту сведений и применимые нормативные условия.
4. **Обратная связь.** Пользователь видит недостающие сведения, требования и их основания.
5. **Отправка.** При выполнении условий заявка передаётся работодателю; блокирующие требования препятствуют отправке.
6. **Рассмотрение.** Исполнитель работает с заявкой, историей и ответами.
7. **Контроль.** Руководитель получает агрегированные показатели процесса.

## 3. Основные возможности

| Направление | Возможности |
|---|---|
| Подготовка заявок | Создание обращения, заполнение полей, сопровождение пользователя |
| Проверка требований | Контроль обязательных сведений, блокирующие условия, необходимость подтверждения работодателя |
| Нормативные основания | Отображение цитат и ссылок на применимые положения |
| Работа исполнителя | Очередь заявок, карточка, история, подготовка ответа |
| Уведомления | Информирование о событиях и изменении состояния заявки |
| Контроль процесса | Журнал действий, история переходов, агрегированные метрики |
| Автоматизация | Инфраструктура для фоновых задач и служебных агентов |

## 4. Роли пользователей

- **Заявитель** — создаёт заявку, заполняет сведения, отправляет её и отслеживает состояние.
- **Модератор / исполнитель** — обрабатывает очередь, изучает карточки и историю, готовит ответы.
- **Руководитель** — просматривает агрегированные показатели без отображения имён заявителей.
- **Служебные агенты** — предусмотрены для автоматизированных операций; их доступ управляется отдельным служебным токеном.

## 5. Архитектура

Система построена как набор взаимодействующих компонентов с разделением пользовательского интерфейса, API, хранения данных и асинхронной обработки событий.

| Компонент | Технология | Назначение |
|---|---|---|
| Web | Gleam / Lustre, Nginx | Пользовательский интерфейс |
| API | Gleam / Wisp | HTTP API и обработка запросов |
| Database | PostgreSQL | Заявки, справочники, нормативные данные, события и аудит |
| Message broker | NATS JetStream | Асинхронная доставка событий |
| Outbox relay | Go | Передача событий из outbox в NATS |
| Consumer | Go | Фоновые обработчики и служебные агенты |

### Схема взаимодействия

```text
        Заявитель / Исполнитель / Руководитель
                         |
                         v
                  Web-интерфейс
                  Lustre + Nginx
                         |
                         v
                    API (Gleam)
                         |
             +-----------+-----------+
             |                       |
             v                       v
         PostgreSQL              HTTP API
             |
             v
          Outbox
             |
             v
       Outbox relay (Go)
             |
             v
       NATS JetStream
             |
             v
       Consumer (Go)
             |
             v
       Фоновые задачи
       и агенты
```

### Архитектурные принципы

- **Разделение ответственности:** пользовательский интерфейс, API, хранение и фоновые процессы развиваются независимо.
- **Асинхронная обработка:** события передаются через outbox и NATS JetStream.
- **Идемпотентность:** повторная доставка событий должна учитывать защиту от дублирования операций.
- **Прослеживаемость:** история действий и нормативные основания позволяют анализировать ход обработки заявки.
- **Контролируемые решения:** блокирующие требования проверяются системной логикой, а не свободной интерпретацией текста.

## 6. Надёжность и контроль

В проекте предусмотрены механизмы:

- проверки состояния API через `/health` и `/ready`;
- хранения событий для последующей передачи через outbox;
- доставки событий в NATS JetStream;
- контроля повторного применения seed-данных;
- фиксации истории и нормативных оснований решений;
- блокировки отправки при выполнении условий hard-stop.

Для ключевых сценариев предусмотрены автоматические проверки API, интерфейса и E2E-проверки блокирующих требований.

## 7. Текущее состояние проекта

Проект содержит работающий локальный демонстрационный контур с API, веб-интерфейсом, базой данных, NATS JetStream и фоновыми компонентами.

Подготовлены сценарии проверки входа, создания заявок, блокирующих требований, подтверждения работодателя и успешной отправки.

**Важные ограничения текущей версии:**

- Тип заявки «Служебная командировка» пока отключён (`enabled=false`) до юридической сверки нормативных цитат по первоисточникам.
- Для демонстрации доступен синтетический тип «Учебная поездка (DEMO)».
- DEMO-учётные записи и пароли предназначены только для локального тестирования.
- Текущая версия не заявляется как готовая к промышленной эксплуатации.

Таким образом, демонстрационный контур подтверждает работу отдельных пользовательских и технических сценариев, но не заменяет юридическую проверку нормативной базы и полноценную оценку производственной безопасности.

## 8. Перспективы развития

Дальнейшее развитие предусматривает применение языковых моделей для обработки естественного языка и документов.

В качестве одного из вариантов локального запуска моделей рассматривается **Ollama**.

Потенциальные направления:

- интеллектуальная классификация обращений;
- извлечение сведений из документов;
- подготовка черновиков заполнения;
- формирование уточняющих вопросов;
- анализ обезличенных причин возврата заявок.

При этом нормативные проверки, обязательные условия и блокирующие решения должны оставаться в детерминированном программном контуре. Результаты модели не должны подменять нормативные основания или подтверждённые сведения.

Интеграция Ollama и её испытания относятся к будущим задачам развития, а не к подтверждённым возможностям текущей версии.

## 9. Локальный запуск (Windows, PowerShell)

Для запуска демонстрационного стенда необходимы Windows 11, PowerShell и Docker Desktop с Docker Compose v2.

```powershell
# Перейти в каталог проекта
cd C:\home\Agents\effectivnost-360

# Создать локальную конфигурацию
Copy-Item .env.example .env

# Заполнить обязательные параметры в .env

# Собрать образы
docker compose build

# Запустить сервисы
docker compose up -d

# Проверить состояние
docker compose ps
```

При необходимости применить миграции и seed-данные:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\apply_db.ps1
```

Основные адреса локального стенда:

| Компонент | Адрес |
|---|---|
| Web-интерфейс | http://localhost:8050/ |
| API | http://localhost:8000/ |
| Проверка API | http://localhost:8000/health |
| Проверка готовности | http://localhost:8000/ready |

Подробные инструкции по настройке, ролям, тестовым сценариям и устранению ошибок приведены в руководстве по локальному запуску.
