# CJM → карта экранов «Эффективность 360»

**Дата:** 2026-10-23
**Версия:** 1.0
**Назначение:** документ фиксирует, где в репозитории найден исходный пользовательский
сценарий (CJM), как этапы CJM соотносятся с экранами интерфейса и какие API-вызовы
за каждым экраном стоят. Документ — основание для реализации, а не описание уже
сделанного.

## 3. Карта экранов

| Этап CJM | Экран/страница | Цель пользователя | Основные действия | Источник данных/API |
|---|---|---|---|---|
| **Начало пути**<br>«Открыть сервис, понять, что это» | **S0. Старт**<br>(`/`) | Увидеть, что сервис помогает оформить заявку, и понять, куда вводить текст | Прочитать назначение; нажать «Описать запрос» | Статический. Данных с сервера нет |
| **Описание запроса**<br>«Свободным текстом описать командировку» (CustDev §5 задача) | **S1. Описание**<br>(`/describe`) | Сформулировать поездку своими словами, не зная требований | Ввести текст; нажать «Создать черновик» | `POST /api/v1/requests` → 202 `{request_id, created}` |
| **Разбор и уточнения**<br>«Система классифицирует/извлекает → задаёт вопросы только о недостающих полях с пункком/цитатой» | **S2. Уточнения**<br>(`/request/{id}`) | Понять, что именно не хватает, и **увидеть основание** каждого требования | Прочитать извлечённые поля; прочитать основание (clause_id + дословная цитата); дозаполнить поля | `GET /api/v1/requests/{id}` → `{id,status,request_type,fields,submitted_at,created_at}`; `POST .../submit` → 422 `{complete:false, missing[]}` |
| **Проверка и отправка**<br>«Детерминированно проверяет полноту» | **S3. Проверка** (часть S2)<br>кнопка «Отправить заявку» | Понять, что заявка полна, и отправить её | Заполнить последнее поле; нажать «Отправить»; при 422 — дочитать основание | `POST /api/v1/requests/{id}/submit` → 200 `{status:"submitted", submitted_at}` |
| **Результат**<br>«Разрешает отправить готовую заявку» | **S4. Результат**<br>(`/request/{id?submitted`) | Убедиться, что заявка принята, и понять, что будет дальше | Прочитать статус и время подачи; увидеть, что повторная отправка заблокирована | `GET /api/v1/requests/{id}` → `status:"submitted"` |
| **Возврат и разбор ошибок**<br>«Что было непонятно / какие уточнения понадобились» | **S2 + S4 (ошибка)** | Понять, что пошло не так | 422 → список missing; 409 → «уже отправлено»; 404 → «заявка не найдена»; сеть → «API недоступен» | Тот же `POST .../submit`; ошибки классифицируются по телу ответа |
| **Восстановление после F5**<br>«Как узнавал статус» (CustDev §2 Q9) | **S2/S4 с восстановлением** | Не потерять заявку при перезагрузке страницы | Открыть страницу заново → состояние подтягивается с сервера | `GET /api/v1/requests/{id}` (id из URL-роута, **не** из localStorage) |

## 4. Почему именно такой набор экранов

1. **S0 обязателен** — `docs/tz/CustDev.md` §5 требует: «Сначала дайте задачу без
   объяснения интерфейса и не подсказывайте порядок действий». Стартовая страница не
   должна подсказывать порядок шагов — значит, без «пошагового мастера» с
   подсветкой следующего шага. S0 даёт только назначение и одну точку входа.
2. **S1 обязателен** — вход в сценарий A: свободный текст (`docs/Readlog.md` §«Цели P0»).
3. **S2 объединяет «разбор» и «уточнения»** — потому что CustDev §5 Q4 спрашивает
   «Что для вас означает ссылка на пункт положения?» и §5 Q5 «В какой момент вы
   решили, что заявку можно отправлять?». Экран, на котором одновременно видны
   *извлечённое*, *недостающее* и *основание требования*, отвечает на оба вопроса
   сразу. Разносить их на два экрана — значит заставлять пользователя держать
   в голове контекст.
4. **S4 обязателен** — `docs/tz/Check-point.md` §6 требует «Статусы сохраняются».
5. **Восстановление после F5 обязательно** — CustDev §2 Q9 «Как узнавал статус?».

**Что НЕ создаётся** (сознательно):
- отдельный «мастер» с прогресс-индикатором (мешает CustDev §5);
- панель исполнителя, дашборд руководителя, админка положения (v0.2, §12.4);
- отдельная страница «мои заявки» — API `GET /api/v1/requests` (список) не существует,
  а `requester_id` отсутствует (аутентификация не реализована). Экран «список
  заявок» был бы фиктивным.

## 6. Навигация

- **Маршрутизация — на стороне сервера (nginx)**, не в Lustre: `/` → S0, `/describe` → S1,
  `/request/<id>` → S2/S4. Причина: после F5 браузер должен восстановить состояние
  **с сервера** (CustDev §2 Q9), а не из памяти клиента. Lustre-роутинг с
  `history.pushState` дал бы «пустой» экран после перезагрузки на произвольном URL.
- nginx дополнительно проксирует `/api/` → `api:8000` (reverse proxy). Это убирает
  CORS-зависимость и позволяет браузеру использовать **относительные** `/api/...`
  вместо недоступного браузеру `http://api:8000`.
- **Кнопка «Назад»** — браузерная (обычная навигация). Отдельной «Назад» в UI нет:
  в сценарии A всего три перехода, и лишняя кнопка вводила бы в заблуждение.
- **Переход «Назад» из S2 в S1** — да, есть: «Описать заново» (создаёт новый черновик
  с новым idempotency-ключом; старый остаётся в БД как `draft`).

## 7. Что экраны берут с сервера, а что — локально

| Данные | Источник | Примечание |
|---|---|---|
| `request_id`, `status`, `request_type`, `fields`, `submitted_at`, `created_at` | `GET /api/v1/requests/{id}` | Единственный источник истины |
| `missing[]` (field_name, required, conditional, reason, clause_id, quote) | `POST .../submit` → 422 | Сервер — единственный источник оснований |
| Тип заявки и её поля (для формы) | `GET` → `request_type` + `fields` | **Не** захардкоженный список — сервер возвращает фактические `fields` |
| Список полей для отрисовки формы | Локальный список `field_specs` в UI | Это **подписи и порядок**, а не значения. Значения — из сервера |
| `raw_text` | **не отображается и не запрашивается** | API его не возвращает |

**Важно:** список подписей полей в UI — это представление, а не источник требований.
Основания (`clause_id`, `quote`) приходят **только** с сервера в ответе 422. UI не
имеет права показывать основание, которого не вернул сервер.
